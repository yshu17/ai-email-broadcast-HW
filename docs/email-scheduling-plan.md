# План: планирование отправки email-кампаний

Дата подготовки: 2026-09-24
Репозиторий: https://github.com/ievgiienko/ai-email-broadcast
Локальная копия: корень репозитория

Документ описывает текущую архитектуру отправки, план добавления
запланированной отправки («Schedule») с сохранением немедленной отправки
(«Send now»), критерии приёмки и открытые вопросы. Реализация на этом этапе
**не выполняется**.

---

## 1. Текущая архитектура

Стек: Next.js 16 (App Router) + TypeScript + PostgreSQL + Drizzle ORM +
Nodemailer. Один процесс, одна база данных, без Redis/очередей-брокеров.
Очередь отправки живёт целиком в Postgres.

### 1.1. Путь «создание кампании → отправка»

1. **UI создания/редактирования** — [`CampaignWizard.tsx`](src/app/(admin)/campaigns/[id]/CampaignWizard.tsx)
   четырёхшаговый визард (Compose → Recipients → Preview → Send).
   Шаг Send — [`SendStep`](src/app/(admin)/campaigns/[id]/CampaignWizard.tsx:391),
   кнопка «Queue campaign» → подтверждение в модалке → `POST /api/campaigns/{id}/send`.
2. **Список рассылок** отображается через
   [`CampaignDetail.tsx`](src/app/(admin)/campaigns/[id]/CampaignDetail.tsx:13):
   пока `status === "DRAFT"` показывается визард (контент редактируемый),
   иначе — [`CampaignReport.tsx`](src/app/(admin)/campaigns/[id]/CampaignReport.tsx)
   (статус, статистика, Pause/Resume/Cancel). Контент кампании **замораживается**
   после выхода из DRAFT — это уже существующее правило, важное для дизайна планирования.
3. **API отправки** — [`src/app/api/campaigns/[id]/send/route.ts`](src/app/api/campaigns/[id]/send/route.ts):
   проверяет DRAFT-статус, subject, compiledHtml, наличие SMTP-настроек;
   делает условный `UPDATE ... WHERE status = 'DRAFT'` (побеждает только один
   параллельный запрос → 409 остальным), затем вызывает
   `generateRecipients()`. Само письмо здесь **не отправляется** — только
   ставится в очередь.
4. **Материализация очереди** —
   [`generateRecipients()`](src/lib/campaign-recipients.ts:111): собирает
   контакты выбранных списков, дедуплицирует по email
   (`dedupeCandidates`), убирает адреса из глобального suppression-листа,
   вставляет по одной строке `campaign_recipients` на адрес со снапшотом
   контакта, `ON CONFLICT DO NOTHING` по `UNIQUE(campaign_id, email_normalized)`.
5. **Фоновый обработчик** — `POST /api/worker/tick`
   ([`src/app/api/worker/tick/route.ts`](src/app/api/worker/tick/route.ts)),
   авторизация по `WORKER_SECRET`. Вызывает
   [`runTick()`](src/lib/worker.ts:54):
   - возвращает просроченные лизы в очередь (`reclaimExpiredLeases`);
   - читает расход часового лимита (`countSentInLastHour`);
   - вычисляет размер батча (`batchSize` в [`src/lib/rate-limit.ts`](src/lib/rate-limit.ts:34));
   - атомарно захватывает получателей одним `UPDATE ... FOR UPDATE OF r SKIP LOCKED`
     ([`claimRecipients()`](src/lib/queue.ts:124)) — это то, что делает
     параллельные вызовы cron безопасными;
   - повторно проверяет suppression-лист;
   - отправляет письма через Nodemailer с ограниченным параллелизмом
     ([`sendBatch()`](src/lib/worker.ts:145));
   - помечает `SENT` / `FAILED` / ставит retry с backoff (1 → 5 → 15 минут);
   - завершает кампании без оставшихся `QUEUED`/`SENDING` строк
     (`finalizeCompletedCampaigns`).
6. **Кто вызывает `/api/worker/tick`** — деплой-зависимо: `npm run worker`
   ([`scripts/worker-loop.ts`](scripts/worker-loop.ts)) в дев-режиме и на
   Docker/VPS (`RUN_INTERNAL_WORKER=true`), `vercel.json` cron
   (`* * * * *`) на Vercel Pro, либо внешний cron (cron-job.org, GitHub
   Actions) в остальных случаях. **Никакого таймера в процессе приложения
   или в браузере не используется** — это и есть образец того паттерна,
   который нужно повторить для планирования.

### 1.2. Модель данных (только релевантное для планирования)

[`src/lib/db/schema.ts`](src/lib/db/schema.ts):

- `campaignStatusEnum` (строка 21): `DRAFT | QUEUED | SENDING | PAUSED | COMPLETED | CANCELLED`.
- `campaigns` (строка 143): `status`, `startedAt`, `completedAt`, `totalRecipients`,
  контентные поля. **Нет** полей для времени отправки/часового пояса.
- `campaignRecipients` (строка 173): `deliveryStatus`
  (`QUEUED|SENDING|SENT|FAILED|SUPPRESSED|CANCELLED`), `nextAttemptAt`
  (уже используется для backoff — семантически близко к тому, что нужно для
  планирования, но на уровне получателя, не кампании), `leaseExpiresAt`,
  `claimedBy`.
- Миграции лежат в [`drizzle/`](drizzle) (например
  [`0001_delivery_cancelled.sql`](drizzle/0001_delivery_cancelled.sql) —
  `ALTER TYPE ... ADD VALUE`), генерируются `npm run db:generate` из схемы.

### 1.3. Проверки доступа

Единый админ, сессии в cookie (`mailer_session`, hash в БД) —
[`src/lib/auth.ts`](src/lib/auth.ts). Все мутации проходят через
[`withAuthMutation()`](src/lib/api.ts:29) → `requireAdminMutation()`:
проверка сессии + `Origin` (CSRF). `/api/worker/tick` — отдельная модель
доступа, по `WORKER_SECRET`/`CRON_SECRET` в заголовке (не сессия админа),
см. [`authorize()`](src/app/api/worker/tick/route.ts:17).

### 1.4. Часовой пояс и время в проекте сегодня

Все временные метки в БД — `timestamp with timezone` (Postgres
хранит как UTC). В UI дат/времени для ввода нет вообще — ближайший
аналог часового пояса, который видит пользователь, это оценка
длительности рассылки (`estimatedDuration`,
[`src/lib/rate-limit.ts:58`](src/lib/rate-limit.ts:58)). Библиотек для
работы с датами/часовыми поясами в зависимостях нет (`package.json`) —
проект нарочно избегает лишних зависимостей (см. `README.md`, раздел
«Architecture and trade-offs»: свой CSV-парсер вместо библиотеки, свой
редактор вместо TipTap). Для планирования это значит: конвертацию
локальное время → UTC разумно делать через встроенные `Date`/`Intl`, без
добавления `date-fns`/`luxon`, если возможности браузера/Node этого
достаточно (см. раздел 3.3).

## 3. Рекомендуемое решение

### 3.1. Новый статус кампании: `SCHEDULED`

Расширить `campaignStatusEnum`:
`DRAFT → SCHEDULED → QUEUED → SENDING → (PAUSED) → COMPLETED / CANCELLED`.

`SCHEDULED` — отдельный статус, а не флаг на `DRAFT`, по тем же причинам,
по которым в проекте уже разделены `delivery_status` и engagement-поля
(комментарий в `schema.ts:30-38`): статус должен однозначно отвечать
«что сейчас с кампанией», а «когда её запустить» — это данные, а не
пересчитываемое состояние.

Переходы:
- `DRAFT → SCHEDULED`: `POST /api/campaigns/{id}/schedule` с телом
  `{ scheduledAt: string /* ISO-8601 UTC */, timezone: string /* IANA */ }`.
- `SCHEDULED → DRAFT`: `POST /api/campaigns/{id}/unschedule` (отмена
  расписания, кампания снова редактируема).
- `SCHEDULED → QUEUED`: автоматически воркером, когда `scheduled_at <= now()`.
- `DRAFT → QUEUED`: как сегодня, через `/send` (немедленная отправка).

Как и переход `DRAFT → QUEUED`, переход `DRAFT → SCHEDULED` и
`SCHEDULED → QUEUED` — условные `UPDATE ... WHERE status = X`, что даёт ту
же защиту от двойного запуска при параллельных запросах/тиках, что и
сегодня (комментарий в `send/route.ts:11-19`).

### 3.2. Данные о расписании

В `campaigns` добавить:
- `scheduledAt: timestamp("scheduled_at", { withTimezone: true })` —
  момент отправки в UTC (Postgres хранит `timestamptz` как UTC
  внутренне, независимо от пояса клиента).
- `scheduledTimezone: text("scheduled_timezone")` — IANA-имя пояса,
  который выбрал пользователь при планировании (`"Europe/Kyiv"` и т.п.),
  **только для отображения**. Хранить его нужно, чтобы корректно
  показать «Запланировано на 30 сентября, 14:00 (Europe/Kyiv)» даже если
  сервер/просматривающий администратор находится в другом поясе — без
  этого поля нельзя восстановить исходный локальный час из одного лишь
  UTC-инстанта при DST-неоднозначностях.

Индекс `(status, scheduled_at)` — под запрос промоушена, по аналогии с
существующим `campaign_recipients_claim_idx`
(`schema.ts:214`, `(delivery_status, next_attempt_at)`).

### 3.3. Клиент: ввод даты/времени и часовой пояс

- Переключатель radio «Send now» / «Schedule for later» в `SendStep`.
- При выборе «Schedule»: `<input type="datetime-local">` (локальное
  время браузера, без пояса в значении) + нередактируемая подпись
  часового пояса, определённого автоматически:
  `Intl.DateTimeFormat().resolvedOptions().timeZone`.
- Конвертация в UTC перед отправкой на сервер: `datetime-local` даёт
  компоненты локального времени; `new Date(y, m, d, h, min)` в браузере
  создаёт `Date` в **локальном** поясе браузера автоматически, и
  `.toISOString()` возвращает корректный UTC — сторонняя библиотека для
  этого шага не нужна.
- Клиентская проверка: `scheduledAt > Date.now()` — блокирует кнопку и
  показывает инлайн-ошибку до сабмита (UX, не единственный источник
  истины).
- Отображение назад (в `CampaignReport`, списке кампаний): взять
  сохранённые `scheduledAt` (UTC) и `scheduledTimezone`, форматировать
  через `new Intl.DateTimeFormat("ru", { timeZone: scheduledTimezone, dateStyle: "medium", timeStyle: "short" }).format(new Date(scheduledAt))`.
  Не нужна арифметика со смещениями вручную — `Intl` сам учитывает DST
  для указанного IANA-пояса на указанную дату.

### 3.4. Сервер: валидация будущей даты

В `POST /api/campaigns/{id}/schedule`:
- `scheduledAt` обязателен, парсится как ISO-строка, должна быть
  валидной датой.
- `timezone` обязателен, IANA-строка (валидировать через
  `Intl.supportedValuesOf("timeZone").includes(timezone)` либо через
  `try { new Intl.DateTimeFormat("en", { timeZone: timezone }) } catch`).
- Проверка «в будущем» — сравнение с `now()`, взятым **на сервере**
  (`new Date()`), а не доверять клиентскому времени. Небольшой запас
  (например, отклонить только если `scheduledAt <= now()`, без доп.
  буфера) — сервер является источником истины по времени, а рассинхрон
  часов клиента не должен давать ложных 400.
- Так же, как `/send` сегодня, проверить subject/compiledHtml/SMTP
  заранее — не откладывать эти проверки до момента фактического
  промоушена, чтобы ошибка была видна сразу при планировании, а не через
  дни при срабатывании.

### 3.5. Надёжный фоновый запуск запланированных кампаний

**Не** таймер в процессе и **не** браузерный `setTimeout`/`setInterval` —
явное требование задачи, и в проекте уже есть готовый паттерн для этого:
`/api/worker/tick`, вызываемый внешним планировщиком (cron/Vercel Cron/
`worker-loop.ts`) независимо от того, открыт ли браузер или жив ли
конкретный процесс приложения.

Решение: расширить `runTick()`
([`src/lib/worker.ts:54`](src/lib/worker.ts:54)) новым первым шагом —
**промоушен** запланированных кампаний, до захвата получателей:

```ts
// src/lib/queue.ts
export async function promoteScheduledCampaigns(): Promise<string[]> {
  const rows = await sql<{ id: string }[]>`
    UPDATE campaigns
    SET status = 'QUEUED', updated_at = now()
    WHERE status = 'SCHEDULED' AND scheduled_at <= now()
    RETURNING id
  `;
  return rows.map((r) => r.id);
}
```

```ts
// src/lib/worker.ts, в начале runTick()
const promotedIds = await promoteScheduledCampaigns();
for (const id of promotedIds) {
  try {
    const result = await generateRecipients(id);
    if (result.total === 0) {
      // см. открытый вопрос 4.4 — что делать при пустой аудитории на момент срабатывания
    }
  } catch (err) {
    // см. раздел 3.6 — обработка ошибок промоушена
  }
}
```

Почему этого достаточно и не нужен отдельный планировщик/очередь задач:
дополнительный триггер (например, Vercel Cron с более частым интервалом)
не требуется — существующий тик уже вызывается не реже раза в минуту в
рекомендуемых деплойментах, а промоушен — это один дешёвый `UPDATE`,
который не мешает основной работе тика при отсутствии due-кампаний.
Задержка срабатывания ограничена интервалом тика
(`WORKER_TICK_INTERVAL_SECONDS`, по умолчанию 60 c), что приемлемо для
кампании, а не для точного до секунды таймера.

### 3.6. Защита от гонок и обработка ошибок промоушена

- **Гонка нескольких обработчиков**: `UPDATE ... WHERE status = 'SCHEDULED' AND scheduled_at <= now()`
  без предварительного `SELECT` — Postgres сериализует конкурирующие
  `UPDATE` над одной и той же строкой: вторая транзакция блокируется до
  коммита первой, затем её `WHERE` переоценивается и строка уже не
  `SCHEDULED` → не задета. Ровно тот же механизм, что уже используется
  для `DRAFT → QUEUED` (`send/route.ts:36-40`) и для
  `markCampaignsStarted` (`queue.ts:234`). Отдельный `SKIP LOCKED` тут не
  нужен — `SKIP LOCKED` в `claimRecipients()` нужен для *чтения+выбора*
  под конкурентную нагрузку, а здесь простой `UPDATE ... WHERE` уже даёт
  ровно один успешный переход на кампанию.
- **`generateRecipients()` идемпотентна** (`ON CONFLICT DO NOTHING`) — даже
  если промоушен по ошибке случится дважды для одной кампании (не должно,
  но на случай будущего рефакторинга), повторный вызов не создаст
  дублей.
- **Ошибка при `generateRecipients()` после промоушена** (например,
  временная недоступность БД между `UPDATE` и `INSERT`): кампания уже
  `QUEUED`, но без получателей. Рекомендация — откатывать статус обратно
  в `SCHEDULED` в `catch`, чтобы следующий тик повторил попытку
  автоматически (retry «бесплатно», через штатный механизм тиков, без
  отдельной retry-логики):
  ```sql
  UPDATE campaigns SET status = 'SCHEDULED' WHERE id = $1 AND status = 'QUEUED'
  ```
  Ошибку логировать через `console.error` (как уже делает `tick/route.ts:36`),
  без падения всего тика — одна проблемная кампания не должна блокировать
  остальные.
- **Пустая аудитория на момент срабатывания** (например, все контакты
  удалены/отписались после планирования) — см. открытый вопрос 4.4.

### 3.7. UI отображения запланированного времени и статуса

- `StatusBadge` — добавить `SCHEDULED` в `STATUS_COLORS` (`ui.tsx:70`),
  например синим/amber, отличным от `QUEUED`.
- `CampaignReport`/`CampaignDetail` — для `SCHEDULED` показать
  «Запланировано на {локальное время в scheduledTimezone}», кнопку
  «Отменить расписание» (→ `/unschedule`) рядом с местом, где сегодня
  Pause/Cancel для `QUEUED`/`SENDING`.
- Список кампаний (`CampaignsClient.tsx`) — показать запланированное
  время вместо/рядом с `startedAt` для строк в статусе `SCHEDULED`.

### 3.8. Сохранение немедленной отправки и проверок доступа

- `POST /api/campaigns/{id}/send` не меняется по контракту (тот же
  запрос, тот же немедленный переход `DRAFT → QUEUED`); внутренняя
  реализация может переиспользовать общую функцию с `/schedule` для
  проверок subject/body/SMTP, чтобы не разойтись логикой.
- Новые эндпоинты `/schedule` и `/unschedule` используют тот же
  `withAuthMutation()` (`api.ts:29`) — сессия администратора + проверка
  `Origin`, без исключений. `/api/worker/tick` остаётся на
  `WORKER_SECRET`, никакой новый публичный доступ не появляется.

## 4. Открытые вопросы (нужно решение продукта до реализации)

### 4.1. Изменение и отмена расписания
Что делает «Отменить расписание» — возвращает кампанию в `DRAFT`
(снова редактируемую) или переводит в терминальный `CANCELLED`
(как сегодня для уже запущенных кампаний)? Рекомендация: `DRAFT`, так как
ничего ещё не отправлено и естественно дать возможность просто
перепланировать/отредактировать. Требует подтверждения.

### 4.2. Редактирование запланированной кампании
Можно ли редактировать subject/контент/список получателей, пока кампания
`SCHEDULED`, или это запрещено (как сегодня запрещено для `QUEUED`, см.
`CampaignDetail.tsx:9-12` — «content is intentionally frozen once a
campaign leaves DRAFT»)? Рекомендация: заморозить, как и `QUEUED` —
изменения требуют сначала `unschedule` → `DRAFT`. Проще в реализации и
не создаёт риска редактирования «прямо перед выстрелом». Требует
подтверждения.

### 4.3. Момент фиксации списка получателей
Список получателей формируется в момент планирования (`schedule`) или в
момент фактического срабатывания (`promoteScheduledCampaigns`)? План
выше рекомендует — **в момент срабатывания** (см. 3.5), чтобы список
оставался актуальным до последнего момента (совпадает с философией
«queue не отправляет» и с текущим поведением `/send`, которое тоже
формирует список непосредственно перед постановкой в очередь, а не
заранее). Альтернатива — фиксировать сразу при планировании, чтобы
администратор видел точный список получателей заранее и мог его
проверить; это будет отличаться от текущей архитектуры (пришлось бы
завести отдельное «предпросмотровое» состояние очереди). Требует
подтверждения выбора.

### 4.4. Поведение при пропуске времени отправки из-за простоя
Если воркер не вызывался длительное время (простой хостинга, падение
cron) и `scheduled_at` уже сильно в прошлом на момент восстановления —
отправлять ли кампанию немедленно при первом тике после восстановления,
или это должно требовать подтверждения администратора, если опоздание
превышает некий порог (например, «более чем на N часов»)? Рекомендация
по умолчанию — отправлять всегда, без порога (простое поведение,
совпадающее с тем, как уже ведёт себя реклейм лиз получателей —
`reclaimExpiredLeases()` ничего не спрашивает, просто продолжает).
Если для продукта важно не разослать сильно устаревшую кампанию без
подтверждения (например, «утренняя» рассылка, отправленная ночью после
восстановления сервиса, теряет смысл) — нужен порог и статус вроде
«пропущено, требует подтверждения» вместо автоматической постановки в
очередь. Требует решения продукта.

### 4.5. Пустая аудитория на момент срабатывания
Если к моменту срабатывания в выбранных списках не осталось получателей
(все удалены/все в suppression) — `generateRecipients()` вернёт `total: 0`.
Текущий `/send` в этом случае откатывает кампанию обратно в `DRAFT`
(`send/route.ts:46-53`) и возвращает ошибку **вызывающему запросу**.
У автоматического промоушена нет вызывающего пользователя, которому
можно вернуть 400. Рекомендация — откатить в `DRAFT` и явно пометить
кампанию как «расписание отменено: аудитория пуста» (нужно поле для
такого сообщения — либо переиспользовать `lastError`-подобное поле на
уровне кампании, которого сегодня нет, либо ограничиться логом сервера).
Требует решения, насколько заметным для администратора должно быть это
событие.

Сделано:

- **Список кампаний** (`CampaignsTable.tsx`, вынесен из `CampaignsClient.tsx` ради тестируемости):
  `SCHEDULED` со своим цветом бейджа, строка «Scheduled for …» только у `SCHEDULED` (без времени — без

  считается одним SQL-запросом `estimateRecipients`, т.к. до старта `total_recipients = 0`). Фильтра по
  статусу и сортировки в списке нет — добавлять нечего.
- **Отмена:** `POST /api/campaigns/:id/cancel-scheduled` → `cancelScheduledCampaign()` в
  `campaign-activation.ts`: условный `UPDATE … WHERE id = $1 AND status = 'SCHEDULED'`. Отдельно от
  существующего `/cancel` (тот отменяет и `QUEUED`, что здесь недопустимо). Повтор по `CANCELLED` — `200`
  с `alreadyCancelled: true`; иной статус — `409`; нет кампании или не-UUID — `404`. Тело запроса игнорируется.
  `scheduled_at` сохраняется. Диалог подтверждения (`CancelScheduledDialog.tsx`) общий для списка и
  страницы кампании.
- **Гонка отмены и запуска:** обе стороны — условные переходы из `SCHEDULED` над одной строкой. Отмена после
  активации ждёт коммита транзакции запуска и получает `409`; запуск при незавершённой отмене пропускает
  строку (`SKIP LOCKED`), а после её коммита не находит `SCHEDULED`. Заранее созданных заданий нет —
  очередь строится при старте, отменять в ней нечего.
- **Часовые пояса:** единый модуль `src/lib/scheduling.ts` теперь работает с явной IANA-зоной (по
  умолчанию — зона браузера, `getUserTimeZone`), без `Date`-методов локальной зоны. Несуществующее время
  (весенний перевод) — ошибка у поля времени; неоднозначное (осенний перевод) — мастер показывает оба
  варианта со смещениями UTC и просит выбрать (`occurrence: "first" | "second"`). Отображение — только через
  `formatScheduledTime` / `<ScheduledTime>` (локаль пользователя + краткое имя зоны). Отдельное поле
  `scheduledTimezone` не добавлено: абсолютный момент хранится в UTC, а читать его каждый должен в своей зоне.
- Миграций на этом этапе нет.

Решение по вопросу 4.1: «отмена расписания» = терминальный `CANCELLED` (по требованию этапа), а не возврат
в `DRAFT`. Возврат в `DRAFT`/перенос времени и 4.2 (редактирование `SCHEDULED`) остаются открытыми.
Модели владения кампанией в проекте нет (один тип администратора), поэтому «чужой» кампании не существует:
защита — сессия, same-origin и `404` для несуществующих id.

## 11. Статус реализации: этап 4 (перезапуск и восстановление)

Разбор текущего механизма: расписание — строка `campaigns` (`status = SCHEDULED`, `scheduled_at`); поиск —
`activateDueCampaigns()` в начале каждого `runTick()` (`scheduled_at <= now()`, часы БД); активация —
`queueCampaign()`: одна транзакция (`FOR UPDATE SKIP LOCKED` → `QUEUED` → запись получателей); таймеров в
памяти нет; тикер — `npm run worker` / sidecar контейнера / внешний cron.

Найденные пробелы и что сделано (минимально, без нового сервиса и без миграций):

- **`QUEUED` без получателей навсегда.** Текущий код так не делает (транзакция), но такое состояние могло
  остаться от старой версии или от старого инстанса во время выката; ничто его не разбирало
  (`claimRecipients` брать нечего, `finalizeCompletedCampaigns` завершает только `SENDING`). Добавлен
  `recoverStuckCampaigns()` (в каждом тике, после активации): `QUEUED` без строк получателей старше
  `STUCK_CAMPAIGN_GRACE_SECONDS` получает очередь под блокировкой строки (`ON CONFLICT DO NOTHING`), а при
  пустой аудитории — `CANCELLED` (ничего не отправлено, `COMPLETED` было бы ложью).
- **`QUEUED` с полностью завершённой очередью без единого захвата** (например, все отписались до первого
  тика) оставалась в `QUEUED`. `finalizeCompletedCampaigns` теперь завершает и такие, но не `QUEUED` без строк.
- **Лимит пачки 25 и упорно падающие кампании.** Активация идёт страницами: упавшие не расходуют лимит
  (`SCHEDULER_BATCH_LIMIT`, по умолчанию 100), поэтому «отравленные» кампании не вытесняют остальные.
- **Потеря соединения с БД посреди цикла.** Первая ошибка соединения (`isConnectionFailure`) завершает цикл
  (`connectionLost`), а не перебирает все кампании против недоступной БД; остальные остаются `SCHEDULED`.
- **Тикер (`scripts/worker-loop.ts`)** вынесен в `src/lib/worker-loop.ts`: таймаут запроса, быстрые повторы
  после сбоя (5, 10, 20 с … до интервала), один цикл на процесс, штатная остановка. Sidecar в
  `docker-entrypoint.sh` перезапускается, если завершился.
- Тесты: `worker-loop`, `scheduler-recovery`, `scheduler-restart`, `scheduler-processes` (реальные процессы:
  `SIGKILL` посреди активации, два планировщика одновременно, цепочка перезапусков с лимитом SMTP,
  миграции при старте, скрипт тикера). Часовой пояс тестов зафиксирован в `tests/env.ts` (`UTC`,
  переопределяется `TZ=`).

Остаточные риски: отправка «хотя бы один раз» — если процесс умер после того, как SMTP принял письмо, но до
`markSent`, то после истечения аренды (`QUEUE_LEASE_SECONDS`) получатель будет отправлен повторно (это
свойство очереди до планирования, не изменялось); sidecar-тикер — один процесс на контейнер.
